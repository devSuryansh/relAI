Plug in your agent

Definition

An agent, in relAI, is any object with a name and a run method that takes a task and returns a trajectory. The lab does not need to know how the agent thinks. It needs the steps. Tool calls go through the suite's environment, so the same faults and the same prices apply to your agent and to the baselines.

Why this helps you

This is the page the rest of the tour is for. Point the lab at the agent you already have, and it will run the same tasks, the same number of trials, and the same broken tool calls as a baseline. A higher score then means your agent handled the failure. You can read the failure labels and see whether you should add a retry, stop a loop, or stop calling a tool you were never given.

Try this

Route every tool call through the recorder. A timeout comes back as a result with ok false and a fault name. You decide whether to retry. This agent looks up one order and retries that call once.

from relai import FaultPolicy, Variant, load_suite, make_baseline, run_experiment


class MyAgent:
    name = "mine"

    def __init__(self, env):
        self.env = env

    def run(self, task):
        rec = self.env.recorder(task)
        rec.plan("look the order up")
        result = rec.call("order_status", {"order": "O-88121"})
        if not result.ok:
            rec.recovery("retry once")
            result = rec.call("order_status", {"order": "O-88121"})
        if result.ok:
            return rec.final(result.output)
        return rec.final("unknown")


suite = load_suite("reliability")
env = suite.env(FaultPolicy(timeout_rate=0.3))
experiment = run_experiment(
    suite.tasks[:1],
    [
        Variant("mine", MyAgent(env)),
        Variant("naive", make_baseline("naive", env)),
    ],
    trials=5,
)
for row in experiment.summary():
    print(row["variant"], f"{row['success_rate']:.2f}")

From the terminal, point --agent at a factory that takes a ToolEnv. The repository includes one:

relai run reliability --agent examples.custom_agent:make_agent --agent retry:2 --timeout-rate 0.3

examples.custom_agent:make_agent means the function make_agent in that module. It receives the suite's environment. The variant is named by the agent's name attribute.

What you should see

The script prints two lines for the order-status task, five trials, seed 0:

naive 0.80
mine 0.80

The CLI command prints the usual table. One run of it in this repository, with a single trial per task, put stubborn and retry:2 both at success 1.00. Stubborn is the name of the example agent. Both follow the suite's reference plan. Stubborn allows up to five attempts on a call. retry:2 allows the original call plus two retries.

How to read it

On this seed, both agents miss one of the five trials, and each miss is a recovery failure. Naive gives up when the first call times out. Yours tries once more, and that second call times out too. One retry is not a guarantee. It only covers a fault on the first call. The faults page is the same suite with three retries, where success reaches 1.00.

Compare your row with the baseline in the same command, not against a number from another day. Same suite, same trials, same seed, same faults. Then read the failure modes line for your agent.

  • Mostly recovery: the agent is giving up, or retrying in a way the recorder cannot see.
  • Mostly tool misuse: it is calling a tool the task did not allow, or passing the wrong argument name.
  • Mostly context: it is repeating a call it already got an answer for.
  • Mostly horizon: retries, or a long plan, are blowing the step budget. The answer may still be right.
  • Mostly planning: it is answering without the tools the task needed.
  • Unclassified: the answer is wrong and none of those rules explain it. Look at the trajectory in the HTML report before you invent a cause.

The agent contract page is the small interface written out. Live models is the same contract backed by an API. Your own suite is how you replace the customer-support tasks with the tasks your agent actually faces.

Easy to mix up

Calling a tool yourself, and not through rec.call, hides the call. The lab cannot inject the fault, the price and the latency never get recorded, and the trajectory looks like the agent never tried. Recording a retry without rec.recovery(...) still retries the tool, but the report cannot tell a deliberate retry from an accidental second call. Write the recovery step.
