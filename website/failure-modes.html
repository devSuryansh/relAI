Failure modes

Definition

A failure mode is a label the classifier puts on a trajectory, with a sentence of evidence. There are five: planning, tool misuse, context, recovery, and horizon. A run can carry more than one. The root cause is whichever label has the earliest evidence. A failed run that matches none of the five stays unclassified. The classifier does not guess.

Why this helps you

A failed score tells you the answer was wrong. It does not tell you what to change. These labels are the change list. Planning means the agent never did the work. Tool misuse means it used a tool badly. Context means it ignored something it had just been told. Recovery means a tool failed and the run never got back on a working path. Horizon means it ran too long or never answered. If you are tuning your own agent, you want to know which of those you are looking at before you add retries, prompts, or tools.

Try this

The same run as the faults page. Read the failure modes lines under the table.

relai run reliability --agent naive --agent retry:1 --agent retry:3 --trials 5 --timeout-rate 0.3

What you should see

failure modes (retry:3): {'horizon': 12}
failure modes (retry:1): {'recovery': 14, 'horizon': 2}
failure modes (naive): {'recovery': 25}

How to read it

The rules, in the order the classifier checks them. A label is added only when its evidence is present. Successful runs skip the planning check.

ModeWhen it firesA run it must not catch
planning The answer is wrong, and the run has no tool error. Typical evidence: a task that requires tools was never given a tool call, a task tagged planning has no plan step, or the answer is wrong with no tools and no errors. A wrong answer that followed a timeout. That is recovery, or tool misuse, not a missing plan.
tool misuse A call names a tool outside allowed_tools, or a call fails and the next step is not an environment error. Unknown tools and bad arguments land here, because they are the agent's mistake. A timeout. The recorder writes an error step after the call, so the failure belongs to the environment.
context The agent calls the same tool with the same arguments again after it already received an observation. It ignored new context. A retry of a call that failed. A failed call is followed by an error, not by an observation, so a retry is not a context failure.
recovery An error step never gets a working path back. A path is restored by a later successful call of the tool that failed, or by a correct final answer. If the agent does not even record a recovery step, the evidence says so. A chain of retries that ends in success. Every error in that chain counts as recovered, and the mode stays silent.
horizon The trajectory has more steps than max_steps, or it ends with no final answer. This one can fire on a run whose answer was right. A long run that still fits under the task's step budget and does finish.

Counts are across runs, and one run can add to more than one count. Naive's 25 recovery labels are the timeouts it did not retry, across 12 tasks and 5 trials (60 runs). retry:3 recovered from those timeouts, so its recovery count is zero, but 12 of its runs crossed a step budget. The answers were still right, which is why success is 1.00 and horizon is not. pass^k stays 1.00 there because the score, not the horizon label, decides a pass.

Unclassified is a failed run the rules do not explain. The lab leaves it unlabeled on purpose. Forcing it into the nearest mode would make the classifier look more certain than it is. The self-check page shows that the labels above really do match agents built to fail in one known way.

Easy to mix up

Root cause is not "the only thing that went wrong". It is the earliest label. A run can misuse a tool and then also fail to recover. The table of failure modes counts every label. Root cause, used by the self-check, keeps one. Also, a horizon flag on a correct answer is not a wrong answer. Read the success column and the horizon count together.
