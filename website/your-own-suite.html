Your own suite

Definition

Your own suite is a YAML or JSON file that lists the tasks you care about, the tools those tasks call, how an answer is judged, and the faults you want by default. relai run path/to/suite.yaml treats that file the same way it treats the name reliability.

Why this helps you

A good score on the customer-support desk does not mean your agent can do your job. The desk is a stand-in with known answers, so the lab can be tested. Your suite is how the same machinery scores the prompts, tools, and answers you actually ship. Because the tools are tables, you can run the suite in CI without the real services, and you can still inject timeouts into those tables.

Try this

Save this as my-suite.yaml. It is one lookup tool and one task. normalized accepts "Shipped" as well as "shipped".

name: my-suite
scorer: normalized
tools:
  order_status:
    arg: order
    cost_usd: 0.001
    latency_ms: 100
    responses: {O-1: shipped}
faults: {timeout_rate: 0.2}
tasks:
  - id: status
    prompt: What is the status of order O-1?
    expected: shipped
    allowed_tools: [order_status]
    tags: [requires_tools]
    max_steps: 8
    guess: processing
    solution:
      - {tool: order_status, args: {order: O-1}}
relai run my-suite.yaml --agent naive --agent retry:1 --trials 5

The file's timeout_rate applies because the command does not pass --timeout-rate. Pass the flag when you want to override it.

What you should see

Seed 0, five trials of the one task:

variant  success  95% CI        pass^k  consistent  cost     latency  recovery  horizon
-------  -------  ------------  ------  ----------  -------  -------  --------  -------
retry:1  1.00     [1.00, 1.00]  1.00    1.00        $0.0012  300ms    1.00      4.6
naive    0.80     [0.80, 0.80]  0.00    0.00        $0.0010  280ms    0.80      4.0

failure modes (retry:1): none
failure modes (naive): {'recovery': 1}

retry:1 vs naive on 5 paired runs: retry:1 alone passed 1, naive alone passed 0; McNemar p = 1.0000 (not significant)

How to read it

Naive passes four of the five trials. The fifth times out and is a recovery failure, so pass^k is 0: not every trial succeeded. retry:1 covers that one timeout. The interval for naive is [0.80, 0.80] because there is only one task to resample, so the bootstrap cannot move. A paired test on a single disagreement is not significant (p = 1). The same command with the same seed repeats these numbers. Add tasks before you trust a p-value.

The fields you will reach for first:

  • scorer. exact, contains, normalized, numeric, or regex. --scorer overrides the file. Numeric reads the first number in the answer. Regex uses expected as the pattern.
  • tools. kind: lookup is the default. kind: calculator evaluates an expression argument. arg is the parameter name your agent must use. The wrong name is tool misuse, not a fault.
  • responses. Input text to output text. Matching ignores case and extra spaces. An unknown input returns default, or "no result".
  • faults. timeout_rate, error_rate, fail_first_n, and an optional tools list. Rates must add up to at most 1.
  • solution and guess feed the baselines and the self-check. A chain may use "{0}", "{1}", and so on for earlier outputs. Your agent can ignore the solution and still be scored against expected.

JSON works too, with the same keys, if you would rather generate the file. load_suite accepts either. Keep expected answers short if you are using exact or normalized match, or switch to contains when the agent wraps the answer in a sentence.

Easy to mix up

A suite tool is not your production API. It is a table that stands in for one, so faults and prices are repeatable. When you want the real model against these tables, use the live model adapter. When you want the real API, you still route that call through the recorder, and you accept that a live service will not follow the seeded schedule unless you inject the fault yourself before the call returns.
