Features

Trajectories

Definition

A trajectory is the ordered list of steps in one run. A step is a plan, a tool call, an observation, an error, a recovery, or a final answer. Steps can carry latency, token counts, and cost. The final answer is the content of the last final step. If there is no final step, the run has no answer.

Why this helps you

Everything you see in a table was derived from these steps, and nothing else. If a number looks wrong, the trajectory is the place to look, not the agent. You can save the steps, diff them, and replay the score without spending another model call. That is also why a new failure mode has to be pinned with a trajectory fixture in the tests: the rule has to be visible in the steps.

Try this

Build a one-step trajectory in Python. This is the same shape the recorder builds for you.

from relai import Step, Trajectory

traj = Trajectory(steps=[
    Step.plan("look it up"),
    Step.tool_call("order_status", {"order": "O-88121"}, ok=True),
    Step.observation("shipped"),
    Step.final("shipped"),
])
print(traj.final_output)
print([step.kind.value for step in traj.steps])

What you should see

shipped
['plan', 'tool_call', 'observation', 'final']

How to read it

The six kinds, and who writes them:

  • plan. You write it with rec.plan("..."). The planning check looks for it on tasks tagged planning.
  • tool_call. rec.call(name, args) writes this, including whether the call was ok, the tool's price, and its latency.
  • observation. The tool's output, written automatically after a call that was not an injected fault. A bad argument is also recorded here, because it is not an environment fault. The text is the error message.
  • error. Written automatically when the fault policy returns a timeout or an outage. The content looks like timeout: order_status timed out.
  • recovery. You write it with rec.recovery("retry once") when you decide to try again. The classifier uses this step to tell "gave up" from "tried and still failed".
  • final. rec.final("shipped") ends the run and returns the trajectory. rec.stop() ends the run with no answer, which is a horizon failure.

The harness adds two keys to task.metadata before it calls your agent: relai.trial and relai.seed. You rarely read them. The tool session reads them so the fault schedule stays aligned across agents. If your agent raises, the harness replaces the trajectory with a single error step and the experiment continues.

The HTML report prints every step of every run. That view is described on Reports.

Easy to mix up

An observation is not always good news. A call that fails because the argument name is wrong is still an observation, with tool_ok false, and it counts as tool misuse. An injected timeout is the path that writes an error step. Also, final_output is the last final step, not the last observation. If you forget rec.final, the scorer sees no answer.
