Definition

A live model agent is the same contract backed by an OpenAI-compatible chat endpoint. OpenAICompatAgent asks the model, runs the tool calls it requests through the suite's ToolEnv, and repeats until the model answers or the turn budget runs out. Tokens, cost, and latency are recorded on the steps. Hosted APIs and a local server such as Ollama both fit, because both speak that HTTP shape.

Why this helps you

The offline baselines tell you the lab works. They do not tell you whether your model handles a timeout. This adapter puts that model in the same table as retry:2, with the same faults and the same scorer. You can see whether the model retries when the system prompt asks it to, whether it loops, and what the tokens cost. You do not write a second evaluation path for "real" agents.

Try this

The example script loads the reliability suite at a timeout rate of 0.2, runs your model for three trials, and writes live_report.html beside a retry:2 baseline.

OPENAI_API_KEY=sk-... RELAI_MODEL=gpt-4o-mini python examples/live_llm_agent.py

A local model, with no hosted key:

OPENAI_BASE_URL=http://localhost:11434/v1 RELAI_MODEL=qwen2.5:7b python examples/live_llm_agent.py

Optional prices, in dollars per thousand tokens, are RELAI_USD_PER_1K_PROMPT and RELAI_USD_PER_1K_COMPLETION. Leave them at 0 if you only want token counts. The agent's constructor also takes max_turns (default 8), temperature (default 0), and a system_prompt. The default prompt tells the model to use tools when it needs data, to retry a tool that times out, and to finish with the answer only.

What you should see

This page does not paste a live score. The numbers depend on the model, the key, and the day. What the script prints is one summary line per variant, the model and retry:2, each with a success rate and a failure-count dict. It then writes live_report.html, which is the same report format as any other experiment. Open that file to see the model's steps: the tool it called, the timeout if one was injected, whether it called the tool again, and the final answer.

If you have no endpoint, skip the command. The rest of the site is runnable without one. Come back when you want the model in the table.

How to read it

The adapter builds a recorder for the task and sends the tool schemas from the environment, restricted to the task's allowed tools when that list is set. Each model turn becomes steps. A transport error is an error step, not a crashed experiment. If the model is still calling tools when max_turns is spent, the run stops short of a normal answer and is classified as a horizon failure.

Faults apply because the tools are called through the ToolEnv, not because the adapter has its own fault logic. The baseline in the same run_experiment call shares that environment, so it meets the same schedule when it makes the same calls. A model that calls a different tool, or calls it a different number of times, can meet a different draw. The schedule is per tool and per call number. It is not "the nth HTTP request".

Compare the model with the baseline on success, pass^k, and the failure line, the same way the faults page compares naive with retry. A model that scores like naive is giving up after the first timeout. A model that scores like retry and also shows context failures is retrying and then repeating work it already finished.

Easy to mix up

The adapter does not grade the model's reasoning. The scorer sees the final answer only. A long, correct explanation can fail an exact or normalized scorer if the expected text is the single word shipped. The default system prompt asks for the answer alone for that reason. Also, a local server must actually be running at OPENAI_BASE_URL. A refused connection is recorded as an error step on the runs that needed the model.
