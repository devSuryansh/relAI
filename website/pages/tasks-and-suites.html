Definition

A suite is the experiment's world: the tasks, the tools those tasks may call, how answers are scored, and any faults that should apply unless the command line overrides them. A task is one question, with an expected answer and the tools it is allowed to use.

Why this helps you

The built-in suites are enough to see the lab work. They are not your product. A suite file is how you describe the jobs your agent actually does, with tools that return the kinds of answers those jobs need, without waiting on the real network. Once that file exists, every command on this site accepts its path in place of the name reliability.

Try this

relai suites
relai run demo

The demo suite is the smaller of the two. Its weather tool always fails the first call, and only an agent that retries can finish that task. The reliability suite is a customer-support desk: lookup tools for customers, orders, shipping, refunds, stock, exchange rates, and weather, plus a calculator. It has 12 tasks, from one call up to five. It injects no faults until you pass --timeout-rate or --error-rate.

What you should see

demo          3 tasks  Three small tasks for a first look: ...
reliability  12 tasks  A customer-support desk backed by lookup tools. ...

One task from the reliability suite, shortened from the YAML, shows the shape. {0} means the output of the first call, and {1} the output of the second:

- id: latest_order_status
  prompt: What is the status of the latest order placed by ravi@example.com?
  expected: delivered
  allowed_tools: [customer_lookup, order_history, order_status]
  tags: [requires_tools, long-horizon]
  max_steps: 12
  guess: shipped
  solution:
    - {tool: customer_lookup, args: {email: ravi@example.com}}
    - {tool: order_history, args: {customer: "{0}"}}
    - {tool: order_status, args: {order: "{1}"}}

How to read it

  • expected is what the scorer compares with the final answer. This suite uses normalized match.
  • allowed_tools is the permit list. A call outside it is tool misuse.
  • tags such as requires_tools tell the planning check that skipping tools is a failure. planning requires a plan step.
  • max_steps is the horizon budget. Longer trajectories are flagged even when the answer is right.
  • guess is what the guessing baseline answers, so the self-check knows that agent will be wrong.
  • solution is the reference plan the offline baselines follow. Your agent does not have to follow it. It is there so the baselines have a known-good path to depart from.
  • answer can stand in for a final answer when a task has no tool plan, such as a direct arithmetic question.

Tools are lookup tables or a calculator. A lookup declares the argument name, a price, a latency, and a map of inputs to outputs. Keys ignore case and extra spaces. A missing key returns the tool's default, which is "no result" unless you change it. The calculator parses arithmetic with a small whitelist of operators. It does not call Python's eval.

Writing a file of your own is the page Your own suite.

Easy to mix up

solution is not a script your agent is forced to run. It is metadata the baselines read. A live model never sees it unless you put it in the prompt yourself. And guess is not the expected answer. It is the wrong answer the guessing agent is supposed to give.
