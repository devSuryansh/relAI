Scores

Definition

A score says whether the final answer passed. The metrics around it say what the run cost. pass@k and pass^k turn repeated trials into a reliability number: the chance that at least one of k attempts succeeds, or the chance that all k of them do. The table's pass^k column is the second one, with k equal to the number of trials.

Why this helps you

Success alone flatters an agent that gets lucky. If an agent passes 4 out of 5 tries, success is 0.80, which looks strong. pass^5 for that task is 0, because a customer who runs the agent five times will not get five good answers. If you are deciding whether to trust an agent with a tool that sometimes times out, pass^k is the number that matches that decision. Cost and latency tell you what the extra retries spent to buy it.

Try this

Same command as the faults page. This time read success, pass^k, consistent, cost, latency, recovery, and horizon.

relai run reliability --agent naive --agent retry:1 --agent retry:3 --trials 5 --timeout-rate 0.3

What you should see

variant  success  95% CI        pass^k  consistent  cost     latency  recovery  horizon
-------  -------  ------------  ------  ----------  -------  -------  --------  -------
retry:3  1.00     [1.00, 1.00]  1.00    1.00        $0.0030  1116ms   1.00      8.8
retry:1  0.77     [0.67, 0.88]  0.33    0.33        $0.0025  947ms    0.79      7.2
naive    0.58     [0.38, 0.77]  0.25    0.33        $0.0016  543ms    0.58      5.0

How to read it

Each cell is an average over the 60 runs (12 tasks, 5 trials), except pass^k and consistent, which are computed per task and then averaged.

  • success. The share of runs whose final answer passed the scorer. The reliability suite uses normalized match: lowercase, punctuation removed, spaces collapsed, then an exact compare. Other scorers are exact, contains, numeric, and regex. Numeric gives partial credit. The others are pass or fail.
  • 95% CI. An interval for the success rate. With one trial per task it is a Wilson interval. With several trials the runs of one task move together, so the lab resamples whole tasks (a cluster bootstrap, seed 0, 2000 draws) instead of pretending the 60 runs are independent.
  • pass^k. For a task with c successes in n trials, pass^k is C(c, k) / C(n, k). The table uses k = n = 5, so the task contributes 1 only when all five trials passed, and 0 otherwise. The column is the mean of that value across tasks. Naive's 0.25 means about a quarter of the tasks were clean every time.
  • pass@k is the other estimator, C being the binomial coefficient: 1 - C(n - c, k) / C(n, k). It is the chance that at least one of k sampled trials succeeds. The default table does not print it. It is on each report as pass_at_k if you use --json.
  • consistent. The share of tasks whose trials all agree: all pass, or all fail. An agent that flips between pass and fail on the same task is not consistent, even if its average success looks fine.
  • cost. Mean dollars recorded on steps. Suite tools declare a price per call. Timeouts are still billed.
  • latency. Mean of the declared step latencies, in milliseconds. It is the suite's model of tool time, not the clock on your laptop. Retries add calls, so they add latency.
  • recovery. Of the error episodes in a run, the share after which a working path came back. A run with no errors scores 1. The column averages that.
  • horizon. Mean number of steps in the trajectory. Longer means more plans, calls, retries, and the final answer.

Correctness sits beside success. For exact, contains, normalized, and regex it is 1 on a pass and 0 on a fail. For numeric it is 1 inside the tolerance, and otherwise one minus the relative error, floored at zero. A wrong but close number can fail and still show partial credit.

Easy to mix up

pass@k and pass^k answer different questions. pass@k asks whether the agent is capable of succeeding if you let it try k times and keep a success. pass^k asks whether every one of those tries succeeds. A high success with a low pass^k is an agent you cannot yet trust. Also, the latency column is not wall-clock time. Wall clock is measured, and it is in the JSON summary as mean_latency_ms, but the table shows declared step time so simulated runs stay comparable.
